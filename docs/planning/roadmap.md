# Plan de desarrollo

Las fases tienen condiciones de salida. No son fechas prometidas. La investigación y los diseños pueden avanzar mientras se prepara la base técnica.

| Fase | Entregable | Condición para avanzar |
| --- | --- | --- |
| 0. Validación local | Zona, deporte, entrevistas y establecimientos candidatos | Problema y operación documentados; disposición real a participar |
| 1. Experiencia | Prototipo de jugador y agenda de propietario | Un organizador y un propietario completan sus tareas con observaciones registradas |
| 2. Base técnica | Expo ejecutable, contratos y entorno de desarrollo | Instalación reproducible, chequeos automatizados y configuración sin secretos |
| 3. Núcleo | Catálogo, búsqueda, agenda y reservas | Permisos y conflictos simultáneos verificados; datos demo diferenciados |
| 4. Operación | Anticipos, cancelaciones, avisos y soporte | Flujo de errores y devoluciones probado; condiciones comerciales definidas |
| 5. Confianza y ofertas | Reseñas y promociones acotadas | Reglas de publicación y costo de promociones verificadas |
| 6. Piloto Android | Versión con establecimientos y jugadores reales | Pruebas de tienda cuando apliquen; métricas y atención de incidencias disponibles |

## Orden sugerido

Validación → diseño → Expo → datos y permisos → catálogo y agenda → reservas → operación de cobros → avisos → reseñas/ofertas → piloto.

La investigación de pagos puede comenzar antes, pero ningún cobro se integra sin garantías de reserva y condiciones de cancelación. Las reseñas requieren reservas completadas; las promociones requieren precios confiables.

## Gestión

Trabajar con los issues del [backlog](backlog.md). Considerar: pendiente, preparada, en curso, en revisión y terminada. Estos son estados de trabajo propuestos; no se ha creado un tablero GitHub Projects.

Limitar el trabajo en curso a una entrega principal por persona. Antes de ampliar alcance, registrar el motivo y el efecto sobre el piloto.
